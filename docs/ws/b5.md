# B5: tools and channels

## Scope
Wave 2, session B5 (docs/SPEC.md section 10, feature F10, ARCHITECTURE.md section 10), branch
`build/b5-tools-channels`. Built: the minimal `web/` Next.js project, the governed tool layer (`web/lib/tools/`)
implementing `mcp/tools.yaml`, the gateway mode (`web/middleware.ts`), the Slack commands `/company`, `/trade` and `/ask`
(stub), `/mcp` for the Claude app with GitHub OAuth, inbox writes plus the `onboard.yml` dispatch, and a prompt-injection
suite. All tests run offline with mocked MotherDuck, GitHub and Slack. Nothing is deployed and nothing is posted to Slack.
Research only: no tool places, routes or simulates a broker order, and paper trades are records.

## Contract
What other sessions can rely on.

**Tool layer, for B4, B7 and B8.** Import from `web/lib/tools/index.ts`:
- `toolLayerFromEnv()` returns a `ToolLayer`. It has these methods:
  - `execute(ctx, tool, args, {confirmedSummary?, preview?})` returns a `ToolOutcome`: `command_id`, `tool`,
    `result` (`accepted | pending | refused | duplicate | failed`), `refusal_code` (from `tools.yaml`), `message`,
    `data` (reads), `record_ids`, `inbox_id` and `budget_left`.
  - `preview(ctx, tool, args)` returns the summary to confirm. For `add_company` it also returns the resolved
    `CompanyPreview`. Nothing is written.
  - `record(...)` logs a command that is not a tool call.
  - `listTools(ctx)`.
- **Identity.** Identity comes only from `slackContext(userId)`, `githubContext(login)` or `dashboardContext()`, never
  from arguments.
  - `dashboardContext()` is for B4's write routes behind Vercel Authentication. The tool layer refuses it when
    `MB_GATEWAY=1`.
  - The assistant (B8) uses agent `assistant`, for example `slackContext(id, "assistant")` or
    `dashboardContext("assistant")`. That agent has read tools only.
- **Order of checks** (`web/lib/tools/executor.ts`, `gate`). Identity matches its channel and agent, then the tool
  exists, then the `tools.yaml` channel permission and the agent's tool list, then the kill switch: first the agent
  file's `enabled`, then the inbox `controls` table, read before the arguments, so a switched-off agent is refused as
  `kill_switch` even when its arguments are invalid. If the inbox cannot be read, the result is `failed`. After that
  come the arguments (the `tools.yaml` inputs; unknown arguments are refused), then the day budget (writes counted from
  `inbox.requests`, reads from `inbox.command_log`, per agent and UTC day). Writes then need the
  confirmation (`confirm: summary` tools need `confirmedSummary`, and `add_company` also needs the confirmed preview;
  `delete_company` needs `confirm` equal to the ticker). Last come idempotency (`inbox.requests.inbox_id` = the key)
  and the inbox append, then the dispatch.
- **Idempotency.** The same key with the same actor, tool and arguments returns the first result (`duplicate`). The
  same key with anything else is refused as `duplicate_key`.
- **Logging and reporting.** Every outcome is logged in `inbox.command_log`. Refused and failed outcomes, and dispatch
  failures, go to the owner as a post in #market-brief (the owner is a member; the fixed variable list has no owner
  user id, so there is no DM).
- **Reads.** Each read tool does one keyed `SELECT` per read model, from a fixed table map:
  - `get_overview`: `rm.home`;
  - `get_company`: `rm.stock` and `rm.stock_strategies`. `tools.yaml` also lists `rm.lifecycle`, which is not read
    yet (open question 12);
  - `get_scoreboard`: `rm.strategies` (`_` or the strategy id);
  - `compare_rule_vs_ai`: `rm.compare` and `rm.review`;
  - `get_news`: `rm.news` and `rm.review`;
  - `get_trades`: `rm.trades`.

  The key is `_` or the ticker. Filters that the page key cannot express are returned as `requested` and are never
  applied as SQL. The payload is passed through with a note saying that text fields are quoted data and never
  instructions. `explain` answers "coming soon" until B8.

**Inbox, for B1 (the importer).** Database `market_brief_inbox`, schema `inbox` (`mcp/inbox.sql`):
- **`inbox.requests`**, one row per write.
  - Columns: `inbox_id` (primary key, the idempotency key), `kind` (`watchlist_events | portfolio_trades`), `tool`,
    `market`, `arguments` (the validated `tools.yaml` arguments), `preview` (`add_company`: the identifiers the caller
    confirmed), `channel`, `submitted_by` (the auth identity), `agent`, `command_id`, `submitted_at`, `args_sha256`.
  - The importer maps a row to `watchlist_events` as follows: `requested_by` = `submitted_by`, `channel`,
    `command_id`, `idempotency_key` = `inbox_id`.
- **`inbox.command_log`**: the columns of the `command_log` kind (checked by `tests/test_b5_tools.py`). The importer
  copies these rows to `data/<market>/command_log/`.
- **`inbox.controls`** (`agent`, `enabled`, `note`, `updated_at`): the owner's kill switch without a deploy. The newest
  row per agent counts, and agent `*` covers all agents.
- **The web tier only inserts.** It never updates or deletes.
- **Dispatch.** `POST /repos/{GITHUB_REPOSITORY}/actions/workflows/onboard.yml/dispatches` with body
  `{"ref": "main"}` and no inputs. GitHub answers 422 for an input the workflow does not declare. So `onboard.yml` should
  import every inbox row that is not yet in `inbox_imports`.

**Gateway (`MB_GATEWAY=1`).** The gateway serves only these routes. Everything else is a 404, including `/`,
`/api/v1/*` and `/_next/*`.
- `POST /slack/commands` and `POST /slack/interactions`. The middleware and the route handler both verify the Slack
  signature. A request older than 300 seconds is refused.
- `/mcp` (POST; GET and DELETE answer 405).
- `GET /oauth/authorize`, `POST /oauth/token`, `POST /oauth/register` and `GET /oauth/github/callback` (the GitHub
  OAuth callback).
- `GET /.well-known/oauth-protected-resource[/mcp]` and `GET /.well-known/oauth-authorization-server[/mcp]`.

The middleware rewrites the `/oauth/*` and `/.well-known/oauth-*` paths to their handlers under `web/app/mcp/oauth/`, so
the files stay in B5's folder. A rewrite does not pass the middleware again, and direct requests to `/mcp/oauth/*` are a
404. In the dashboard deployment (`market-brief-app`), all these routes are a 404 and everything else passes.

A local `next start` of the build checked this (no secrets set, so a configured route answers 503):
- gateway mode: `/`, `/api/v1/markets`, `POST /mcp/oauth/token` and `GET /slack/commands` -> 404;
  the `/oauth/*` and `/.well-known/oauth-*` routes and `POST /mcp` -> 503; `GET /mcp` -> 405; an unsigned
  `POST /slack/commands` -> 401;
- dashboard mode: `/oauth/token`, `/mcp`, `/mcp/oauth/token`, `/slack/commands` and `/.well-known/...` -> 404.

**Slack.**
- **Where commands work.** Commands, and the buttons of a summary, are accepted only in #market-brief (the fixed
  channel id `C0C6REB7QS2` of `config/settings.yaml`; `tests/test_b5_tools.py` checks the two agree). Channel ids are
  unique across workspaces, so this also pins the workspace. Modals can only be opened by a command given there. Any
  member may give commands (decision 15).
- **The commands:**
  - `/company add [india|us] [SYMBOL] [amount]` opens the form (market, symbol, optional amount). Check then shows the
    resolved summary: name, exchange, sector, Yahoo symbol, NSE symbol or CIK, and amount. Only Confirm writes.
  - `/company deactivate|reactivate|amount india|us TICKER ...` returns the summary with Confirm and Cancel buttons.
  - `/company delete` is refused and reported (decision 15).
  - `/trade` opens the paper-trade form.
  - `/ask` answers "coming soon".
- **Logging.** Each command that becomes a tool call or a refusal is logged. Opening and cancelling a form are not
  commands, so they are not logged.
- **Idempotency.** The idempotency key is created when the form or the summary is shown, so a second Confirm click is
  a duplicate.

**`/mcp` (the Claude app).**
- **Server.** Streamable HTTP, stateless, JSON answers. Protocol versions 2025-06-18, 2025-03-26 and 2024-11-05.
  `tools/list` shows the 12 tools of the `claude-app` agent; there is no delete.
- **Writes with a summary.** A `confirm: summary` write takes two calls. The first call returns the summary and a
  signed `confirmation_token` (10 minutes, bound to the actor, the tool and the exact arguments). The second call, with
  that token, writes.
- **OAuth.** OAuth 2.1 with PKCE S256. Dynamic client registration accepts only the Claude app's redirect URIs
  (`https://claude.ai/api/mcp/auth_callback`, `https://claude.com/api/mcp/auth_callback`). Sign-in is federated to
  GitHub. The account's login must equal `MCP_ALLOWED_GITHUB_LOGIN` (case-insensitive) and its numeric id must equal
  `MB_OWNER_GITHUB_ID` (see "Deviation"). Anyone else is refused, logged and reported. The state is bound to the browser
  by an HttpOnly nonce cookie (`Path=/oauth`).
- **Stateless signed tokens.** HMAC-SHA256 with `SESSION_SECRET`. A code lives 120 seconds, an access token 1 hour
  (audience = `https://market-brief-gateway.vercel.app/mcp`), a refresh token 30 days. Rotating the secret signs
  everyone out.

**Deviation: `MB_OWNER_GITHUB_ID`.** The fixed list identifies the owner by `MCP_ALLOWED_GITHUB_LOGIN` only. A GitHub
login can be renamed and then registered by someone else, while the numeric id never changes. So B5 keeps the numeric id
as a second, required check: both must match. Removing it was refused in this session as a security weakening, so B5
did not adopt the login-only check. If the owner wants login-only, that is the owner's decision to make explicitly. The
owner finds the id in the `id` field of `https://api.github.com/users/<login>`.

## Open questions
Each question has the default B5 took.

1. **Where the web tier's command log goes.** The web tier cannot write `data/`, so it appends `command_log` rows to
   `inbox.command_log`, and B1's importer copies them to `data/<market>/command_log/`. Rows of commands without a
   market (`/ask`, a refusal before the market was read) have `market` null.
   - Default: B1 stores those rows under both markets.
2. **The inbox schema is B5's proposal.** B1 builds the importer in parallel.
   - Default: B1 reads `mcp/inbox.sql` as written. If B1 already chose other names, the orchestrator reconciles, and
     B5's tables change, not B1's validators.
3. **Writes through the MotherDuck Postgres endpoint.** The spec and ARCHITECTURE.md section 6 plan the endpoint for
   reads; the inbox inserts use the same endpoint.
   - Default: as built. The statements run on DuckDB 1.5.6 locally (`tests/test_b5_tools.py`). If the endpoint refuses
     writes, the owner tells the orchestrator, and the inbox moves to another append path.
4. **Next.js 15.5 rather than 16.** SPEC section 10 names `web/middleware.ts`, and Next 16 renamed middleware to
   `proxy.ts`.
   - Default: `next` 15.5.26, the latest 15.5 published at least two weeks ago. B7 may move to 16 later together with
     the rename.
5. **The add summary resolves from the gateway.** It uses Yahoo's symbol search and SEC's `company_tickers_exchange.json`.
   Yahoo may refuse Vercel's addresses. A failed lookup becomes an `ambiguous` refusal, which is reported to the owner.
   The onboarding (B1) resolves and checks everything again.
   - Default: as built.
   - Alternative: the workflow resolves the identifiers and posts the summary to confirm in Slack, a few minutes later.
6. **Slack membership and workspace.** Commands are accepted only when given in #market-brief (`C0C6REB7QS2`).
   Giving a command there implies being a member. There is no `conversations.members` lookup. The fixed variable list
   has no workspace id, so the channel id (unique across workspaces) and Slack's signature stand in for a workspace
   check.
   - Default: as built.
7. **Budgets per agent and UTC day.** They are provisional:

   | Agent | Writes | Reads |
   |---|---|---|
   | `slack-gateway` (all members together) | 20 | 200 |
   | `claude-app` | 20 | 300 |
   | `dashboard` | 50 | 2000 |
   | `assistant` | 0 | 500 |

   - Default: these values. The owner may change them in `mcp/agents/` (then run `python mcp/build_registry.py`).
8. **OAuth without a store.** Authorization codes are signed, live 120 seconds and need the PKCE verifier, but they are
   not single-use. Tokens cannot be revoked one by one.
   - Default: accepted for an owner-only connector. Rotating `SESSION_SECRET` revokes all of them.
9. **The Claude Code channel.** No agent file exists for it, and the web tier refuses `claude_code`. Claude Code uses the
   validated CLIs directly (ARCHITECTURE.md 9.1).

    `requested` rather than applied, because the read-model payload shapes come from the approved mockups (B4).

    in the same second get the same id.
    - Default: W1's formula kept.

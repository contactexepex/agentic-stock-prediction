## Contract
- **Loader** (`core/market_config.load_market`, MB_NOW-aware):
  - `cfg["tickers"]` = every collected company (active and inactive, never deleted). A company with an entry in the
    config's `company_meta:` (Wave 5; the legacy `tickers:` before it) keeps that entry (news names, aliases, ADR);
    one added by onboarding gets `{name, yahoo, exchange, nse (India), cik (US)}` from its add event. The
    `company_meta:` key is replaced by `cfg["tickers"]` at its place; a config with both keys is refused.
  - `cfg["sectors"]` = membership rebuilt from the companies' sectors (add event; config `sectors:` for config
    tickers without an add event). Config order kept, new sectors and members after.
  - `cfg["active_tickers"]` = active companies in `cfg["tickers"]` order.
  - Market symbols of role `adr` whose `adr_of` company is deleted are dropped.
  - Implicit seed, so test fixtures and unseeded roots keep working: a legacy `tickers:` entry without a stored add
    event acts as an add from the start of time; a `company_meta:` entry does so only while the market has no stored
    seed event (channel `seed`, checked on the stored rows, never on their visibility). In a seeded market membership comes from the events alone, and a `company_meta:` entry
    never adds a company. `tests/test_lifecycle_company_meta.py` proves the rename changes nothing (load_market, the
    active lists, the accessor, every watchlist state and the command validator, at six clocks per market).
- **Helpers for predict and display code**: `marketbrief.lifecycle.loader.active_tickers(cfg)` and
  `active_sectors(cfg)` (a sector without an active member is left out). A cfg built without the loader counts
  every ticker as active.
- **Accessor** (`marketbrief/contracts/watchlist.py`): `watchlist(market, as_of=None, state="active")` with state
  `active | inactive | deleted | collected`, sorted by sector then ticker; `company(market, ticker, as_of)`;
  `trade_amount(market, ticker, as_of)`.
- **Visibility (no look-ahead)**: an event counts as of T when `effective_from <= T` and `recorded_at <= T`. The seed
  rule: add events with channel `seed` count from their `effective_from` even before their `recorded_at`, because
  they restate the config list that every earlier run used; without it a replay dated before the seeding would see
  an empty watchlist once Wave 5 removes `tickers:`. A row named by a visible row's `supersedes` is dropped.
- **Effective time**: add and delete count from the moment they are recorded; deactivate, reactivate and set_amount
  from the next pre-open run (`pre_open_local` in `config/lifecycle.yaml`: India 07:40, US 07:45 local, on the next
  session of the market calendar); never before the company's newest stored event.
- **Transitions**: add from never-added or deleted; deactivate from active; reactivate from inactive; delete and
  set_amount from active or inactive. Refusal codes: `already_active`, `deleted_needs_new_add`, `etf`, `bse_only`,
  `unknown_symbol`, `validation_failed` (mcp/tools.yaml).
- **Delete**: typed confirmation (`--confirm` must equal the ticker), channels `dashboard` and `cli` only.
- **Idempotency**: a key already used by a stored event returns `{"ok": true, "duplicate": true, "event": <first>}`
  and stores nothing new; every command (accepted, refused, duplicate) gets a `command_log` row.
- **CLI** (`scripts/company.py --market india|us ...`): `add --symbol S [--amount A] [--sector X] [--name N]
  [--skip-backfill]`, `deactivate --ticker T [--reason R]`, `reactivate --ticker T`, `set-amount --ticker T
  (--amount A | --default)`, `delete --ticker T --confirm T`, each with `--key K` and `--channel cli|claude_code`
  (requested_by `<channel>:session`); `list`; `seed`; `import-inbox [--inbox FILE] [--skip-backfill]`. stdout is one
  JSON object; exit 2 on a refused write.
- **Onboarding** (`commands.add_company`): pre-check (fields, key, state) -> identifiers (India: NSE equity list
  `EQUITY_L.csv`, NSE quote ETF flag, Yahoo `<SYM>.NS`; a symbol only Yahoo `.BO` serves is `bse_only`. US: SEC
  `company_tickers_exchange.json` on NYSE or Nasdaq, CIK and name from it; Yahoo instrument type must be EQUITY)
  -> sector (`--sector`, else the first `sector_rules` pattern matching NSE's industry info or SEC's SIC
  description; no match: refused with the strings found) -> backfill (prices from the market's first stored day,
  through the price collector's own code; the candidate's Google News query; US filings; India announcements; no
  `news_runs` row) -> the candidate's collect gate (no duplicate ids, a bar for the last completed session, positive
  closes, at least `backfill.min_bars` bars) -> the add event with `onboarding` = each check's result.
  `long_history`: the candidate's Yahoo daily bars from the long-history cache's start (else 15 years back,
  `backfill.long_history_years`), as far as Yahoo has them, merged into `work/model_history/<market>/` (the cache
  `model_history.py` builds for every collected company; gitignored, never data/), its detail giving the years found.
- **Inbox** (for B5's tool layer): database `market_brief_inbox`, table `inbox.company_commands` with columns
  `inbox_id VARCHAR` (the client's idempotency key, 8-64 of `A-Za-z0-9_-`), `market VARCHAR`, `tool VARCHAR`
  (`add_company | deactivate_company | reactivate_company | set_paper_amount | delete_company`), `arguments JSON`
  (`symbol` for add, else `ticker`; `amount`, `reason`, `confirm`), `actor VARCHAR` (the channel's sign-in identity),
  `channel VARCHAR` (`dashboard | slack | claude_code | claude_app`), `submitted_at TIMESTAMPTZ`, `command_id VARCHAR`
  (optional), and optional `slack_channel VARCHAR` and `slack_ts VARCHAR` (the channel and ts of the Slack message the
  command produced, B5): with `--slack-reply` (onboard.yml passes it) and both set, the import replies in that thread
  with the command's `command_log` record through B6's `alerts.onboarding.post_onboarding_confirmation` (once per
  command and result); each import result row carries `command_id` and `slack_reply` (the publish summary, an `error`,
  or null); a Slack failure never stops the import. `onboard.yml` passes `SLACK_BOT_TOKEN` and commits
  `data/<market>/slack_posts/` with the rest of `data/`. The import never deletes inbox rows; an inbox_id with a
  `command_log` row that settled it (accepted, refused, duplicate) is skipped; one whose rows are all `failed` (a
  source did not answer; nothing stored) is tried again by the next import. Inbox rows with channel `cli` or `seed`
  are refused (only dashboard, slack, claude_code, claude_app). The `command_log` row replaces the planned
  `data/<market>/inbox_imports/` kind (ARCHITECTURE.md section 9).
- **Workflow** `.github/workflows/onboard.yml` (workflow_dispatch, input market both|india|us): per market
  `company.py import-inbox --slack-reply`, then B2's `portfolio.py import-inbox` (paper trades from `inbox.requests`,
  issue #112), then commit `data/` with pull --rebase and push, 5 attempts. Secrets: `MOTHERDUCK_INBOX_TOKEN`,
  `SEC_USER_AGENT`, `SLACK_BOT_TOKEN` (Actions secrets). The routine's step 3 runs the same two imports.

## Contract

### Posts
Every post reads stored records through `core.database.connect`, except `intraday --feed`, which reads the given
JSONL file. All reads are as of `core.clock.clock()` (MB_NOW-aware).
Every number in a message is a stored value, or a count, sum or mean of stored values. Every signal line (a pick,
a head-to-head trade, an alert, a settled trade) ends with `[Paper]`. Each message carries "Paper only — no
proven edge yet." and the footer "Research only, not investment advice. Paper trades are records, never orders."

| Subcommand | Reads | Post key | Where |
|---|---|---|---|
| `morning [--date D]` | `strategy_predictions` and `head_to_head_picks` of session D, `made_at <= now` | `morning:<market>:<D>` | the day's thread |
| `intraday [--date D] [--check-id ID] [--feed FILE]` | B9's alerts of the newest check run of D in view `intraday_alerts_feed` with `check_at` and `computed_at <= now` (or `ID`); or B9's alert records in `FILE` with `check_at` (and `computed_at`, when present) `<= now`. The explainer's note only when `explained_at <= now` | `alerts:<market>:<check id>` | the day's thread |
| `close [--date D]` | `paper_trades_settled` of the trades first settled on D (market local date), each as its newest row with `settled_at <= now` (a trade first settled earlier and re-settled on D is a correction of its own day, not a row of D); `eod_analyses` of D | `close:<market>:<D>` | the day's thread |
| `corrections [--days 30]` | for each close post in the ledger posted in the last 30 days: rows with `supersedes` written after that post and by `now`, of trades first settled on its D | `correction:<market>:<row id>` | the thread of D |
| `weekly [--week 2026-W41]` | the newest `research_reviews` row by `now` (of that week) | `weekly:<market>:<iso week>` | its own post |
| `onboarding --command-id ID --channel C --thread-ts TS` | the `command_log` row `ID` with `received_at <= now` and `completed_at` empty or `<= now` | `onboarding:<market>:<ID>:<result>` | a reply to `TS` in `C` |

`D` defaults to `pipeline/market_status.status(cfg, now)`:
- `session_date` for `morning` and `intraday`;
- `previous_session` for `close` (the newest session whose bar is final, which is today at the post-close times
  of SPEC section 7).

Content of each message:
- **Morning.** Top 5 companies by agreement at N+1. Agreement follows DATA_CATALOGUE#agreement and matches
  `agreement.json` on the example predictions. For each company with at least one buyer the message shows:
  - the family split, the average P(up) of the buyers, the average target of the buyers, the last close and the
    company's amount per trade;
  - the strongest other horizon (decision 39: the other horizon with the highest buy count; ties: the shorter;
    "no other horizon has a buyer" when none);
  - each `picked` head-to-head pick: family, pick rule, strategy, horizon, P(up), the prediction's target, the
    expected gain and the amount.

  Empty days:
  - "No proven strong signals today." is always printed (no strategy can be proven before the first go-live
    review, F7.2);
  - "No paper picks today: no strategy buys at N+1." when nothing qualifies;
  - "No paper picks today: no strategy predictions are stored for this session." when nothing is stored;
  - "No head-to-head trades today." for a pick whose picks are all `no_candidate`.
- **Intraday.** One message per check run, from B9's feed:
  - each trade alert (`open_trade_flagged`) not marked `repeat`: one line per flagged trade (horizon, strategy,
    view, move since entry, band, target reached or the distance left, flags), then the deviation explainer's note
    on the check row when it was written by the clock;
  - each news alert (`material_news_open_trade`): status, materiality, title, source, news id and the number of
    open trades on it.

  A run with nothing new posts nothing.
- **Close.** Rule vs AI today:
  - the accuracy view per family (trades, wins with net profit > 0, net profit);
  - the head-to-head view per family and pick rule.

  The totals cover every row settled today. Then the EOD analyst's gated summary, quoted with its id when one
  exists. Then the listed rows (owner, 2026-10-07):
  - every head-to-head row;
  - the 10 biggest wins (net profit > 0, largest first) of the other settled rows;
  - the 10 biggest losses (net profit < 0, largest loss first) of the other settled rows;
  - "…and N more rows settled today on the dashboard." for the rest (break-even, `no_entry` and
    `skipped_price_above_amount` rows included).

  Each listed row shows entry and exit, net profit and return after costs, target reached, range hit and main
  reason code. A `no_entry` or `skipped_price_above_amount` row is not counted as a trade. With no row: "No paper
  trades settled today."
- **Corrections** (owner, 2026-10-07). When a trade is re-settled after its day's close post (a new row with
  `supersedes`, F1.5, e.g. a corrected split), one reply goes into that day's thread: "Correction: *NVDA* N+1,
  Model + news (rule.model_news.v1), accuracy view is now net +$3.10 (+0.31%), was +$4.60 (+0.46%); re-settled
  2026-10-02T03:00:00+00:00 (flags: split_in_window, resettled). [Paper]". The original post stays as posted. A
  re-settlement written before the close post is no correction: the close post already shows the newest row.
- **Weekly.** Leaders per family, findings with their cited ids, proposals with status ("nothing changes until
  the owner approves"), and the report link (`pages_url` + the report path when `pages_url` is set).
- **Onboarding.** "Done / Received, waiting for the import / Not done / Already done earlier / Failed", then the
  command's message, its refusal code, the record ids and the request id.

### The owner's own costs (decisions 50-51; B2's `cost_views`)
The orchestrator relayed the owner decisions 50-51 on 2026-10-07, and the owner confirmed in this session that B6
should build them. B2 stores two cost views for each prediction, pick and settlement in its kind `cost_views`
(docs/ws/b2.md, "Record format: cost_views"): the market cost and "your cost". "Your cost" is the owner's own broker
costs, including BUX's currency conversion and Axis's NRI charges.

`reads.with_costs` joins the newest `cost_views` row computed by the clock onto each record (`record_kind`,
`record_id` = the record's id), under these names (`costs.COST_SOURCES`):

| `cost_views` column | record_kind | Name in the messages |
|---|---|---|
| `your_cost_pct` | `prediction`, `pick` | `your_cost_pct` |
| `expected_gain_your_pct` | `prediction`, `pick` | `your_gain_pct` |
| `your_costs` | `settlement` | `your_costs` |
| `net_pnl_your`, `return_pct_your` | `settlement` | `your_net_pnl`, `your_return_pct` |

The owner decided on 2026-10-07 that "viable" means expected gain after your cost > 0, for everyone. B2 computes it
once (`marketbrief/lab/gain.py`, with the picks' own move and loss) and stores `expected_gain_your_pct` and
`cost_viable` (main a661a56). Slack reads the stored gain and recomputes nothing, so Slack, the picks and the
dashboard agree.

- **Viable** (owner, 2026-10-07): expected gain after your cost > 0. The gain is
  `p × move − (1 − p) × loss − your cost`, the head-to-head formula of F1.7.3 with the owner's cost in place of
  the market costs, all in % of the amount. Example: move +1.00%, P(up) 0.57, loss 2.29% and your cost 0.30% give
  0.57×1.00 − 0.43×2.29 − 0.30 = −0.71%, so the pick is "not viable", although its move exceeds the cost.
- **Morning.** A pick combines several strategies' predictions. Its line ends with "Expected gain −0.71% after your
  cost 0.30% — not viable." (or "— viable."):
  - the gain is the mean of the buying strategies' stored `expected_gain_your_pct` (nulls left out);
  - the cost is the company's stored `your_cost_pct`.

  Each head-to-head line adds "; expected gain −1.44% after your cost 0.30% — not viable" from the pick's own stored
  gain. A record without a stored gain shows no verdict. When at least one pick has a gain and none of them is
  viable, the message says "No pick clears your costs today." right after the header.
- **Close.** Each listed trade shows "net +$4.60 (+0.46%) after $2.34 market costs; after your costs ($2.80) net
  +$4.14 (+0.41%)". Each rule vs AI total adds "(after your costs +$X)" only when every settled row of that total
  has the owner's result (a partial sum would mislead).
- A record without a `cost_views` row computed by the clock shows no cost text; nothing is estimated.

### Live strategies only (B19, Wave 5)
The morning post reads `strategy_predictions` and `head_to_head_picks` directly, so it keeps only rows whose
strategy is live for the session: B2's `marketbrief.lab.registry.is_live(strategy_id, D)` (`live_from` set in

When predictions are stored but none is live, the post says "No paper picks today: no strategy is live for this

### Intraday alerts: B9's feed (`intraday_alerts`, docs/ws/b9.md "The alerts feed")
B6 reads B9's stored feed through the view `intraday_alerts_feed`, which adds the explainer's note. The owner
decided that B6 builds this reader in its own folder (2026-10-07). `--feed FILE` takes the same records as JSONL,

is never posted (it is in the feed and on the dashboard).

### Threads and idempotency (kind `slack_posts`)
- A message longer than 3,500 characters is split on line boundaries. Parts after the first start with
  "(continued i/n)"; a single longer line is cut.
- Each posted part is appended to `data/<market>/slack_posts/YYYY/MM/<posted_at UTC date>.jsonl`:
  - `id` = `<post_key>#<part>`;
  - `kind`, `post_key`, `part`, `parts`;
  - `thread_key` = `<market>:<D>` for thread posts, else null;
  - `channel`, `ts`, `thread_ts` (null for a thread's first message);
  - `text_sha256`, `chars`, `posted_at`, `method_version` `alerts-v1`.
- The day's thread is the first message of the day's first thread post (morning, else the daily brief, else an
  alert, else close).
  Later posts of the day reply to its `ts`, found by `thread_key`.
- A weekly post starts its own thread; its later parts reply to its first part. An onboarding reply goes to the
  given `--thread-ts`.
- A rerun posts nothing for a key whose parts are all in the ledger, even when the text changed: a correction
  is not re-posted. After a failure midway, a rerun posts only the missing parts into the same thread, provided
  the text still splits into the same number of parts. Otherwise it posts nothing more, and the summary says
  `"incomplete": true` with the `missing_parts`.
- A part is recorded after Slack accepts it. A crash between the accepted post and the ledger append makes a
  rerun post that part again: the one case that can double-post.
- The token is read from `SLACK_BOT_TOKEN` and sent only in the Authorization header. Errors carry the API
  method and Slack's error code only, and `SlackClient`'s repr hides the token.
- Webhook fallback (owner, 2026-10-07). Without the token and with `SLACK_WEBHOOK_URL` set, each part goes out as
  its own unthreaded webhook message (`{"text": ...}`), the way `notify_slack.py` falls back.
  - Reruns stay idempotent through the ledger ids (`<post_key>#<part>`), as for every post. The ledger records a
    unique made-up ts `webhook.<12 hex>` and no `thread_ts`. The publish summary's `thread_ts` is null, also on a
    rerun and when a token run meets a post that went out by webhook.
  - An onboarding confirmation through the webhook is an unthreaded message in #market-brief, not a reply to the
    command.
  - A webhook post is never a thread: a later run with the token starts the day's thread.
  - The URL appears in no error, file or repr; a refused post reports only "webhook: HTTP <status> <body>".
- Without the token and the webhook (or with the token but without `slack_channel_id`), a live run exits 2 and
  posts nothing.
- `--feed` times without a UTC offset are read as UTC (data rule 3).
- `--dry-run` posts nothing. It writes each message to `work/alerts_dryrun/<market>/messages.jsonl` (ts
  `dry.000001`, ...) and keeps its own ledger under `work/alerts_dryrun/<market>/slack_posts/`, so dry reruns
  are idempotent too and `data/` is never touched.
- Exit codes: 0 for posted, dry run, or nothing to post; 2 for neither token nor webhook, or no channel; 1 for a Slack or network
  error (`OSError`, `http.client.HTTPException`), or an onboarding command not found as of the clock. A failure never blocks a routine.

### Function for B5 and B1
```python
from marketbrief.alerts.onboarding import post_onboarding_confirmation
post_onboarding_confirmation(command: dict, channel: str, thread_ts: str, *, dry_run=False, http=None) -> dict
```
- `command` is a `command_log` record; `market` is used.
- `channel` and `thread_ts` are the channel and ts of the visible "request received" message B5 posts in
  #market-brief on Confirm (B5's `slack_channel` and `slack_ts` in the inbox, main fcb9869). The confirm summary
  itself is ephemeral or a modal and cannot be threaded.
- The call is idempotent per command id and result, so a `pending` reply and the final `accepted`/`refused`
  reply each post once.
- CLI equivalent: `python scripts/alerts.py --market <m> onboarding --command-id <id> --channel <C> --thread-ts <ts>`.

B5 needs to carry the confirm message's channel and ts through the inbox to the importer (`onboard.yml`), which
then calls this after appending the command's result.
